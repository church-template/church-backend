📝 현재 문제점
---

- 지금은 교회마다 서버, DB, Redis를 따로 띄우는 구조입니다. 코드, 스펙(§2), `CLAUDE.md`, 프로젝트 규칙이 모두 "멀티테넌시를 구현하지 않는다"로 못 박혀 있습니다.
- 운영 서버(OCI, 메모리 1GB)는 앱 1개만으로 메모리 58%, 스왑 21%를 쓰고 있습니다. 교회를 30~40곳 받을 계획인데 교회마다 앱 인스턴스(약 350MB)를 띄우는 것은 물리적으로 불가능합니다.
- 운영자는 1명이라 교회가 늘 때마다 서버를 추가하고 업데이트를 반복하는 방식은 감당하기 어렵습니다.

🛠️ 해결 방안 / 제안 기능
---

- **하나를 모든 교회가 공유합니다.** 앱, DB, Redis를 하나로 두고 모든 테이블에 `church_id`를 추가해 교회별로 데이터를 격리합니다. Hibernate 7이 제공하는 테넌트 기능을 사용합니다.
- **교회 구분은 API 경로 앞부분으로 합니다.** API 도메인은 전 교회 공용 하나이고, 각 교회 프론트의 `NEXT_PUBLIC_API_BASE`를 `https://<공용API>/c/<교회키>`로 바꿔 재빌드·배포합니다. 프론트 코드는 `next.config.ts`의 이미지 허용 패턴 한 줄만 고칩니다.
- **회원, 역할, 직분, 태그는 교회별로 독립입니다.** 같은 전화번호로 교회마다 따로 가입할 수 있습니다. 로그인 토큰에 교회 식별자를 넣어, 다른 교회 주소에서 쓰면 거부합니다.
- **교회 대표자가 그 교회의 `SUPER_ADMIN`입니다.** 지금 역할 구조를 그대로 씁니다. 운영자는 서버와 DB로 접근하므로 앱에 상시 계정을 두지 않고, 교회를 가로지르는 계정도 만들지 않습니다.
- **새 교회 등록은 서버에서 실행하는 SQL 스크립트 하나로 합니다.** 등록 화면과 관리자 API는 만들지 않습니다.
- **파일은 교회별 경로 접두사로 저장합니다.** 기존 은샘 파일은 옮기지 않고, 나중에 S3로 옮길 때는 저장 구현체만 교체하면 됩니다.
- **운영 중인 은샘 데이터는 마이그레이션 1개로 첫 교회로 채웁니다.** 전환 순서는 백엔드 먼저 배포(접두사 없는 옛 주소도 임시로 은샘 처리) → 은샘 프론트 환경변수 변경·재배포 → 임시 처리 제거입니다. 임시 처리를 제거하기 전까지는 이전 버전 재배포만으로 되돌릴 수 있게 합니다. 배포 전에 DB와 업로드 파일을 서버 밖으로 백업합니다.
- **보안을 함께 보강합니다.** 관리자가 자기보다 높은 등급 회원의 비밀번호 초기화·정보 수정을 못 하게 막고, 로그인 시도 횟수를 제한하고, 백엔드 포트를 외부에 직접 열지 않습니다.

비목표: 교회 등록 화면, 플랫폼 관리자 API, 교회별 JWT 시크릿, S3 구현체 자체, DB 레벨 격리(스키마 분리, RLS).
