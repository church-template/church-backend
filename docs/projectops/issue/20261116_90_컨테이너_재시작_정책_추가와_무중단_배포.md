📝 현재 문제점
---

**1. 서버가 재부팅되면 백엔드가 다시 뜨지 않는다**

- 운영 compose(`docker-compose.yml` + `docker-compose.prod.yml`)의 backend·postgres·redis에 `restart` 정책이 없다. 기본값은 `no`다.
- 그래서 서버가 재부팅(보안 업데이트, OCI 유지보수 등)되면 세 컨테이너가 꺼진 채로 남고 사이트가 내려간다. Caddy 컨테이너만 `unless-stopped`라 다시 뜬다.
- 2026-11-16 커널 보안 업데이트 때 이 문제를 발견했다. 운영 서버에서 `docker update --restart unless-stopped`로 임시 조치했다.
- 이 임시 조치는 지금 떠 있는 컨테이너에만 적용된다. 배포 워크플로가 `docker compose up -d`로 컨테이너를 새로 만들면 정책이 다시 `no`로 돌아간다.

**2. 배포할 때마다 사이트가 끊긴다**

- 배포 워크플로(`.github/workflows/deploy.yml`)는 새 이미지를 pull한 뒤 `up -d`로 backend 컨테이너를 교체한다. 옛 컨테이너가 내려간 뒤 새 컨테이너가 응답할 때까지 Caddy는 `502`를 돌려준다.
- 1GB 서버에서 Spring 기동에 걸리는 시간: 2026-11-16 재부팅 직후 실측으로 컨테이너 시작부터 첫 `200`까지 약 2분.
- 배포가 잦아지고 교회 수가 늘수록 이 공백이 문제가 된다. 주일 전후 배포는 더 그렇다.

🛠️ 해결 방안 / 제안 기능
---

- **재시작 정책**: 운영 오버레이(`docker-compose.prod.yml`)의 backend·postgres·redis에 `restart: unless-stopped`를 둔다. 로컬 개발 환경은 바꾸지 않는다.
- **무중단 배포**: 새 backend가 헬스 체크를 통과할 때까지 옛 backend가 요청을 계속 받고, 통과하면 Caddy가 새 쪽으로 넘어가게 한다. 실패하면 옛 backend를 그대로 둔다.

**주의할 점**

- **메모리**: 서버 RAM이 약 1GB다(재부팅 직후 여유 메모리 약 300MB). 무중단 배포는 잠시 backend 두 개를 동시에 띄워야 하므로, 이게 버티는지 먼저 실측해야 한다.
- **첫 배포 때 DB 재시작**: postgres·redis 설정이 바뀌면 다음 `up -d`가 두 컨테이너를 새로 만든다. 그래서 이 변경이 처음 배포될 때 DB·Redis가 몇 초 재시작된다(#86 설계 §6.2 메모와 같은 이유). 데이터는 볼륨에 남는다. 조용한 시간대에 따로 배포한다.
- **배포 경로 일치**: 서버에서 compose를 직접 실행하면 이미지 이름을 못 찾는다(워크플로가 `IMAGE_NAME`·`IMAGE_TAG`를 넘긴다). 무중단 전환 절차도 워크플로 안에서 끝나야 한다.
